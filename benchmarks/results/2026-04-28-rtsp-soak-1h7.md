# 2026-04-28 — RTSP soak, 1.7h, iPhone IP-cam (M3 8-core)

Status: **smoke soak.** Establishes flat-RSS / no-leak signal on a real
RTSP live source. Not the canonical 8h+ acceptance run — see Limitations.

## TL;DR

`Stream.from_url` against an iPhone IP-camera over Wi-Fi held flat
memory (46.3 MB RSS, no growth) for ~90 continuous minutes after a
1-minute warm-up, with zero RTSP timeouts and zero disconnects. The
cold-start reconnect path also exercised cleanly: six "Connection
refused" attempts before the phone listened, then one clean open. No
crash from concealed bitstream errors.

## Hardware

Apple M3 (8-core), 16 GB, GPU none (CPU-only path), Darwin 25.3.0,
rustc 1.91.1.

## Commit

`f8005f9` (feat/mv-step2-h264-extraction)

## Source

iPhone running an RTSP IP-camera app on local Wi-Fi:

```
url       : rtsp://admin:1234@192.168.50.135:8554/live
codec     : H.264, 1920×1080
transport : TCP (default)
```

Phone left on a stationary surface in an empty office. Active human
motion in the first ~18 minutes, then static scene for the remainder.

## Command

```sh
scripts/start-soak.sh   # wraps:
.venv/bin/python scripts/soak.py \
    --rtsp rtsp://admin:1234@192.168.50.135:8554/live \
    --hours 8 \
    --log _soak/run-20260428-191154.log
```

Trigger configuration (in `scripts/soak.py`):
`MotionTrigger(motion_per_mb=5.0)`, `IntervalTrigger(interval_ms=10_000)`,
`SceneChangeTrigger` defaults. `event.decode()` is invoked per fire.

## Findings

1. **No leak.** RSS sat at 46.3 MB for ~90 minutes after the 1-minute
   warm-up. Sampling precision is 0.1 MB so the upper bound on growth
   rate is < 0.07 MB/h. Linear extrapolation says an 8h run would still
   read 46.3 MB.
2. **Cold-start reconnect works in production.** The phone wasn't
   serving when the runner started; the inner FFmpeg-level reconnect
   loop chewed through six refused connects in 60 s and then opened the
   stream. This is the first end-to-end validation of the 002 reconnect
   path against a real device, not a MediaMTX loop.
3. **Idle-state false-positive rate is 0/h.** From t=18 min onwards the
   office was empty. `MotionTrigger` and `SceneChangeTrigger` fired zero
   times across ~90 minutes; only `IntervalTrigger` ticked (every 10 s,
   as configured). This is a wedge signal vs pixel-diff baselines that
   typically fire on sensor noise — to be confirmed by P0.1 in
   `docs/05.exec-plans/004-positioning.md`.
4. **CPU per stream w/ decode ≈ 29% of one core.** Density-smoke
   measured 14.9% for parse-only; this run at 28.8% with `event.decode`
   on every fire is a useful upper bound on the decode tax.

## Limitations

- **1.7h, not 8h+.** Slow leak modes that only show up across many hours
  (FD accumulation across reconnects, page-fragmentation drift,
  thread-local growth) are not exercised. The phone never disconnected
  during the run, so the reconnect-loop path was only hit at cold start.
- **Static scene for 82% of the run.** The flat-RSS conclusion is
  strong, but the workload after t=18 min is essentially "decode + tick
  every 10 s." Active-scene long-run is the canonical acceptance shape.
- **Single stream, single source.** Multi-stream soak is a separate
  axis (covered by P0.3 in 004).
- **Phone IP-cam, not a real CCTV.** Approximation only. Real CCTV
  encoder quirks (low bitrate, long GOP) not exercised.
- **Two earlier launch attempts (`run-20260428-191011.log`,
  `191016.log`) ran in parallel before being killed.** Their logs are
  retained for completeness but the canonical run is `191154`.
